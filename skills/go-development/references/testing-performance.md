# Проверки, производительность и диагностика

Читать для тестирования новых контрактов, performance/memory задач, leaks и profiling.
Не включать полный набор инструментов для обычной правки.

## Доказательство поведения

Начни с проверяемого наблюдаемого результата и риска. Используй существующие Make/CI/
Docker targets. Unit/table tests удобны для преобразований и negative paths. `httptest`
проверяет handler и реальный router без внешнего сервера; он не доказывает listener,
сетевые timeout, TLS и shutdown. Для них нужен отдельный runtime сценарий.

Изолированные реальные зависимости проверяют protocol/storage semantics; fakes нужны
для управляемых отказов и порядка. Успешный mock не подтверждает ACL, транзакции,
broker ACK или совместимость реального endpoint. Тестовый трафик направляется только
в разрешённое окружение; чтение учебника не разрешает обращаться к внешним сервисам.

Public API желательно проверять как потребитель. Внутренние тесты допустимы для сложных
правил, которые иначе трудно локализовать; не экспортируй helpers только ради теста.
Fuzzing полезен для parser/codec при чётких инвариантах и бюджете, не обязателен везде.

`-race` проверяет лишь исполненные пути и не исключает логические гонки, leaks, deadlock
или потерю сообщений. `vet`, compile, tests, CI, runtime и business proof имеют разные
границы. Тест concurrent invariants должен проверять результат/порядок, не только гонки.
`t.Parallel` требует независимых state/fixtures. Loop capture проверяй по версии языка
модуля и форме объявления переменных, не вставляй старый shadowing механически.

Для сохранения поведения characterization проходит до/после. Для bugfix покажи red/green,
если воспроизводимый тест соразмерен; для новой функции проверяй новый контракт. Поддерживай
assertions при переносе; удаление инфраструктурной реализации не удаляет бизнес-требования.

Покрытие строк помогает найти непройденные ветви, но не задаёт достаточность проверки.
Не вводи порог 80/100% без требования проекта. Для нового теста выбери существенные
исходы: успех, отказ, границу значения, частичный результат или отмену — по контракту.
Таблица удобна для однотипных случаев; разные lifecycle-сценарии не нужно втискивать
в одну таблицу с множеством переключателей. Mock задаёт наблюдаемый контракт, а не
точную последовательность несущественных внутренних вызовов.

Для fixture, общей с subtests, `t.Cleanup` учитывает завершение дочерних тестов;
обычный defer родителя может закрыть её до исполнения parallel subtests. Cleanup
выполняется в обратном порядке регистрации: сначала cancel/join пользователя ресурса,
затем Close ресурса. `t.Setenv`/`t.Chdir` меняют состояние всего процесса и несовместимы
с parallel test или parallel ancestor. `t.Fatal`/FailNow вызывай из goroutine теста;
worker передаёт результат/ошибку владельцу проверки.

Проверка leaks должна дождаться штатного shutdown; счётчик goroutines без разбора
владельцев ненадёжен. Используй уже принятый leak checker либо targeted join assertions;
не добавляй библиотеку только ради применения навыка и не скрывай неизвестные leaks
широкими исключениями. Для времени и порядка сначала явная синхронизация/управляемые часы;
`testing/synctest` — вариант при подходящей версии и модели задачи, не эмулятор внешнего I/O.

У fuzz-теста задай инвариант: например, round-trip допустимых значений с учётом
канонизации, отказ без panic или сохранение ограничений размера. Входы независимы,
внешние эффекты изолированы, seed corpus содержит граничные случаи. Обычный `go test`
прогоняет corpus, но не означает полноценный поиск новых входов. Найденный минимальный
случай сохраняй как регрессию без чувствительных данных.

## Измерение перед оптимизацией

Сначала измеримый вопрос: CPU, waiting, latency distribution, throughput, allocation churn,
live memory или backlog? Прими критерий достаточности; «быстрее» без нагрузки и baseline
неполно. Сначала исправь корректность; оптимизацию не маскируй под структурный перенос.

Фиксируй SHA/dirty state, Go version, build flags, CPU/quota/architecture, данные, объём,
число workers/partitions/connections, прогрев и кэш. Baseline/candidate получают одинаковые
входы. Проверяй реальную форму и размер данных после mapping/encoding, а не только raw input.
Укажи, что моделировано (sleep/fake response) и чего такой замер не доказывает.

Не измеряй варианты на фоне конкурирующей тяжёлой работы. Повторы и чередование вариантов
помогают оценить шум; отдельный запуск выявляет влияние предыдущего варианта/GC. Сравни
распределения и практическую величину эффекта, а не единичное ns/op. Облачное/виртуальное
окружение допустимо, если отражает задачу и его шум учтён; не обещай лабораторную точность.

Benchmark измеряет реальную операцию: проверь работу setup/timer, использование результата,
compiler elimination и allocations из harness. Используй поддерживаемые версией средства
`testing` и принятый стиль; не обновляй проект только ради нового benchmark API.
`-race`, profiler, tracing и подробное логирование меняют стоимость: correctness run,
инструментированный диагноз и чистое performance сравнение — разные результаты.

Для повторных замеров используй совместимый с toolchain `benchstat` или принятый аналог:
одинаковые benchmark names/inputs, несколько независимых samples, ns/op, B/op, allocs/op
и существенный для задачи throughput. Статистический сигнал и практическая польза — разные
критерии. `b.Loop` (Go 1.24+) помогает корректно ограничить измеряемый цикл; `b.N` остаётся
допустимым для старой версии и существующих тестов. Не включай setup в замер случайно
и не исключай его, если он является частью пользовательской операции.

## Выбор инструмента

| Вопрос | Первый подход |
|---|---|
| Где тратится CPU? | CPU pprof под представительной нагрузкой |
| Что создаёт много мусора? | alloc_space / alloc_objects и benchmark allocations |
| Что удерживает память? | inuse_space / inuse_objects, ownership/retention, динамика |
| Кто ждёт lock/channel/I/O? | подходящий block/mutex/goroutine profile, затем targeted trace |
| Почему CPU простаивает, есть latency/GC pauses? | короткий runtime trace, задачи/регионы, scheduler/GC events |
| Почему возникла allocation? | compiler escape/inlining diagnostics для точной версии/build |
| Почему pod убит по памяти? | container/process metrics + runtime memory + buffers, не только heap |

Профиль показывает где/сколько, но не всегда причину. Проверяй гипотезу кодом и отдельным
изменением. Выбирай минимально необходимое инструментирование; совместный сбор может
искажать результаты. Не применять флаги и UI-обходы старой версии pprof без проверки.

## GC, память и контейнеры

Различай allocation rate, live heap, retained backing arrays, runtime-reserved memory,
RSS/cgroup usage и configured queue bytes. Короткое плато heap или снижение после GC
не доказывает отсутствие leaks при иной нагрузке или долгой работе. `sync.Pool` может
уменьшить churn, но удерживает память/усложняет ownership; сначала измерь и проверь reuse.

GOGC меняет компромисс CPU/память; GOMEMLIMIT — soft runtime memory limit, не жёсткий RSS
или cgroup cap. Учитывай native/CGo memory, stack/runtime overhead, buffers и запас до OOM.
Не копируй GOGC=1000, частоту GC, 25% CPU или целевые STW цифры из учебного примера как SLA.
Runtime/container-aware GOMAXPROCS зависит от версии языка/toolchain, настроек и среды.
Не переопределяй его вслепую; измерь quotas, throttling и concurrency отдельно.

Предпочти устранить измеренную лишнюю работу/аллокации, сохранив semantics, прежде чем
настраивать GC или раздувать worker pools. Zero allocation не самоцель; полезные копии
могут обеспечивать корректность. Большие buffers не гарантируют больше throughput.

## Диагностика и пределы

pprof/debug endpoints держи за предусмотренной проектом внутренней границей, не публикуй
их вместе с продуктовым API. Profiles, traces и core dumps могут содержать чувствительные
данные. Не добавляй автоматический core dump, SIGQUIT или restart в read-only диагностику:
сигнал может завершить процесс. Для анализа дампа нужны подходящие binary/version/architecture;
аргументы stack trace могут быть неточны из-за ABI, registers и оптимизаций.

В отчёте: контракт, версия, нагрузка, фактические результаты, сравнение, ограничения.
Проверенный маленький benchmark не доказывает production capacity или улучшение всего сервиса.

## Причина результата регрессионного теста

Проверь, что тест достиг нужной границы: ошибка отсутствующей зависимости не
доказывает обработку отказа fetch или публикации. Когда используешь red/green,
запускай один и тот же регрессионный тест на baseline и candidate, проверяй
конкретную причину RED и подготовку до неё. Сохраняй исходные assertions.
Для доказательств фиксируй реально исполненный файл/версию и фазу отказа,
не подменяй фактический результат ожидаемым названием сценария.

При изменении кеширования проверь идентичность всех входов, влияющих на результат.
Совпадение короткого хеша не означает равенства исходного значения. Используй
полный ключ либо проверку равенства внутри hash bucket; сохрани лимиты, lifetime,
владение и синхронизацию. Регрессия должна включать изменение содержимого при
том же ID, когда такой refresh поддерживается. Это функциональная корректность,
её изменение следует явно отделять от переименования.

## Один алгоритм и подменяемые зависимости

Рабочий вход, проверки, порядок эффектов и границы завершения должны оставаться
общими для приложения и тестов. Если ветка или публичный вход существуют только
ради fixture, сначала проверь реальные callers и поддерживаемый контракт. Подмену
переноси на границу эффекта: хранилище, транспорт, часы, генератор. Интерфейс потребителя
или функция описывают нужную операцию, а не весь драйвер; дополнительный interface
не нужен, если существующей функциональной зависимости достаточно.

Fake имитирует тот же контракт операции: сохранение не превращается в чтение,
неизвестный исход не становится успехом. Общие validation, budget и проверки результата
не обходятся тестовым флагом или const TestMode. Подключай реальные зависимости после
необходимой ленивой настройки: раннее создание адаптера может зафиксировать nil-клиент
или ещё не настроенную возможность. Владение и закрытие ресурсов сохраняются.

Нужные только тестам helpers размещай в _test.go или тестовой инфраструктуре.
Перед переносом учти внешние тестовые пакеты и исполняемые fixture-программы:
они не видят методы из _test.go импортируемого пакета. Обновляй их на реальный API,
сохраняя бизнес-утверждения. Отсутствие вызова из одного CLI не доказывает, что API
тестовый. Реальные режимы/протоколы и защитные guards не удаляются по одному имени.

Тесты полного сценария проходят через рабочий вход; отдельный read-only контракт
проверяется на уровне хранилища/связывания данных. Реальные SQL, триггеры, нормализация
и broker ACK продолжают проверяться интеграционно. Fake с готовым результатом не
доказывает эти свойства. При замене fault-hook на порт эффекта проверяй фактический
порядок: например, ACK уже получен, наблюдение потеряно, итог остаётся unknown и
внешний эффект не повторяется.
